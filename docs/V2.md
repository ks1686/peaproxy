# PeaProxy v2 request engine

This is the v2.0.0 request engine. It does not change the schema version.

The request path is still: read the body, keep the exact model unless the caller named an enabled automatic route, choose an account, call the native adapter or a translation, and stop once a stream event is committed.

What changed:

- One attempt budget and deadline cover the whole request. Image calls are not replayed after an uncertain delivery.
- Streams are checked for a valid first event before that event is forwarded. A later failure stays on the same response.
- Cooldowns can name one model. Another model on the same account stays eligible. A cooled account is not probed again until the cooldown ends, and then only one request is the first probe.
- Credential refresh for a single OAuth account is one in-flight call. A newer login is not overwritten by a late refresh.
- `promptCache` defaults to preserve. Optimize adds a breakpoint only for the documented Anthropic profile.
- `pea/auto`, `pea/economy`, `pea/local`, and `pea/free` do nothing until `automaticRoutes.enabled` is true. Exact model ids are not rewritten.
- Response and embedding caches are off unless the matching config flag is set. Cached values stay bound to the account, endpoint, and model.
- `peaproxy clients detect|connect|disconnect|status` edit only the PeaProxy block in Pi, Continue, Codex, and Claude Code configs. `connect opencode` is guided: it prints the preset instead of writing one. Pass `--root` so a command does not touch the real home directory.
- `GET /admin/engine` reports attempt, cache, and route settings without secrets. Client connect and disconnect reject a foreign `Origin` and an unknown name.

Compatibility metadata, when loaded, cannot invent catalog model ids. Unsigned or incompatible metadata is refused and the last good document stays in place. Remote auto-update is off.

Installed harness versions were not live-tested. A fixture or UI smoke that passes does not mean a particular OpenCode, Claude Code, Continue, Codex, or Pi release is supported.

See [CONFIG.md](CONFIG.md) for the fields and [COMPATIBILITY.md](COMPATIBILITY.md) for the metadata rules.

## Unreleased

- The secret store stops waiting when it already knows the answer. A read that holds `secrets.lock` cannot be looking at a half-written `secret.key`, so it reports a wrong-sized key file immediately instead of retrying 50 times over half a second — that loop held `config.lock` and `secrets.lock` to arrive at the same error, on every config load. The retry now lives only on `Get`'s unlocked fallback (permission or read-only filesystem), where a concurrent creator is genuinely possible. A crashed multi-process save converges as before; `TestKeyFileCreatedOnceAcrossProcesses` says so explicitly.
- **One of the two retries in #64 turned out to be load-bearing, and the issue was wrong about it.** The keychain read retry (3 attempts, re-reading a generation replaced mid-read) stays. `secrets.lock` lives in the config directory but the keychain is per-user, so two PeaProxy instances with *different* configs share every item under the `peaproxy` service and share no lock at all — one can republish a generation and delete the old chunks while another is mid-read. The issue assumed only a pre-v2.0.10 binary could do that; any two current instances can. `TestReaderFollowsGenerationReplacedByAnotherProcess` is the proof, and it is why the read is not shrunk.

- `PEAPROXY_DEBUG=1` logs the Claude OAuth tool alias mapping on a 4xx: the account id, the status, and the sorted `client -> upstream` pairs. Client tool names are deliberately sent under Claude Code's names and restored on the way back, because that is the name upstream validates — but it means a `400 tool name ...` names tools the user never wrote, which makes a third-party-app rejection hard to trace. Nothing else is logged: no headers, no request or response body, no tokens. A debug line is still a log line, and logs are what people paste into issues.

- Chat completions on a Codex OAuth account carry `verbosity` and `prompt_cache_key` into the Responses body, as `service_tier`, `reasoning_effort` and `parallel_tool_calls` already did. `verbosity` becomes `text.verbosity` and only for models that implement it — gpt-5, gpt-6, gpt-daybreak and codex-auto-review — because o3, o4-mini and gpt-4.1 reject the field rather than ignoring it; case and surrounding whitespace are normalised, and only `low`, `medium` and `high` pass. `prompt_cache_key` is passed through, and dropped when it is longer than 256 bytes or contains control bytes: it travels in a header, so an unbounded key is an unbounded header.
- `max_tokens` on a Codex chat request is dropped rather than forwarded, and `docs/PROVIDERS.md` now says so. The ChatGPT backend rejects `max_output_tokens` and Codex never sends it, so forwarding one only turns a client’s token cap into a 400.

- A Gemini tool schema with an untyped branch listing several types no longer carries every keyword onto every per-type copy. `{type:[string,number], minLength:1, minimum:0}` produced a number branch with `minLength` and a string branch with `minimum`. Each copy now keeps the keywords that fit its type; `enum`, `const`, `description`, `nullable`, `title` and `default` stay on all of them, and so does `format`, which Gemini accepts on a number as well. A keyword the filter does not know about is kept everywhere — silently dropping a constraint would widen a schema, which is worse than carrying a redundant one.

- An account now keeps one cooldown slot per model alongside its account-wide one. There was a single slot, so a model-scoped failure replaced whatever was stored: a 401 that cooled the whole account was undone by a 429 on another model, and the first model became eligible again. A narrower cooldown never replaces a wider one — cooling one model says nothing about the account's health elsewhere, so it does not reach outside the model it names. `/admin/health` lists every active cooldown rather than one arbitrary entry, so a model that will not route can be traced to the account that is out and why, and a cooldown for a different model no longer makes a request wait for it.

- `/v1/models` lists a model id once. It listed one row per account that could serve the model, so a model three accounts answered showed three times — and OpenAI clients key on `id`, so every picker showed the duplicates. First occurrence wins, and the input is already pin-sorted, so the pinned row is the one kept. `/admin/catalog` is unchanged and still reports one row per account: three accounts serving a model is three facts there, which is a different question.
- The `catalog: N models` line on startup now counts what `/v1/models` will actually serve. It counted every model the gateway knew about, including hidden rows and `<account>:unavailable` placeholders, so a real config printed 11 next to a list of 7.

- Claude and Responses streams now fail over on the same conditions as chat: a retryable error, a transient 502/503/504, or a prelude the stream guard rejected. They previously continued only on a retryable error or a slow prelude, so a 502 went back to the client with other accounts unused — even though the guard had held the bytes back precisely so the request could be retried elsewhere. A slow prelude still moves on without starting a cooldown, as before.
- An `error` chunk arriving before any output on a translated `/v1/messages` or `/v1/responses` stream is now a failed attempt rather than a turn handed back. The adapter closes cleanly after one, so the request was credited as a success and the error returned to a client that had seen nothing. It fails over to the next account without starting a cooldown — an error chunk carries no status to classify, and it is not evidence that the account is unhealthy. Once any output has reached the client the turn is committed and nothing changes: no failover, and the error is what the client gets.

- Every admin and proxy read now requires a loopback `Host`, not just mutations. A page whose DNS is rebound to 127.0.0.1 reaches the server over the loopback interface, so the peer looks local, and it sends the attacker's `Host`; the check that stops it applied only to POST/PUT/PATCH, which left `/admin/usage`, `/admin/requests`, `/admin/accounts` and `/admin/settings` readable by that page. `Origin` and the JSON content-type rule stay on mutations, since a cross-origin GET response is already unreadable without a CORS header PeaProxy never sends. A non-loopback peer is unaffected: with `--allow-lan` the admin token is the control, not the Host.
- A streamed `/v1/responses` reply now carries the model id the client asked for. The translated branches of the Claude and Responses streams wrote straight to the stream guard, past the route rewriter, so a route alias or a suffixed client id showed up as the upstream model in every event, including `message_start`. The native branches already went through the rewriter, so this is the translated paths catching up.
- A streamed `/v1/responses` reply now records its response id and pins the next call to the account that produced it, as the non-streaming path already did. Codex-style clients stream, so a follow-up carrying `previous_response_id` could land on an account that never saw the previous response — which for a provider with per-response state is the wrong account. The id is read from `response.created` and `response.completed` in the bytes the client is sent, and a failed attempt's id is discarded rather than bound.

- A running `peaproxy serve` now watches `config.yaml` and adopts what another process writes to it, within about two seconds: an account added by `auth login`, a catalog/hide/routes edit from the CLI, or a hand edit. Until now those reached a running server only at its next save, which for an idle server is never. Secrets are hydrated for adopted accounts, an invalid file is logged once and leaves the running config alone, and a reload never runs during the server's own save.
- Adoption covers every field read per request — `providers`, `hide`, `expose`, `catalog`, `routes`, `failover`, `automaticRoutes`, `requestEngine`. `failover`, `automaticRoutes` and `requestEngine` were previously merged into the file but never into the running server, so those settings only took effect on the next restart. `bind`, `port`, `allowNonLoopback`, `adminToken`, `requestLog` and `schemaVersion` deliberately still need a restart: a bound listener, a security posture and an open file handle cannot change under live traffic, and `docs/CONFIG.md` now says which is which.

- An account id containing a slash (`work/openai`) keeps its secrets. Secret item keys are `id + "/" + kind`, and parsing cut at the *first* slash, so such an id was read back as the account `work`; the prune that follows every save did not find `work` in the keep set and deleted the secret that had just been written. The account then worked until the process restarted. The split is now on the last slash, which is unambiguous because a kind is never more than one word.
- A merged server save no longer resurrects a secret the user deleted. `keepSecrets` carried the server's in-memory copy forward whenever disk's copy was empty, which also covers a deleted `oauth:` block, a removed keychain item, and an account switched to `apiKeyEnv`; the next save wrote the secret back. Hydration now reports which secrets were *unreadable* (corrupt JSON, undecryptable blob) and only those are rescued from memory. A secret that is merely absent stays absent.
- A wrong-sized `secret.key` no longer spends the whole 500 ms retry budget under both `config.lock` and `secrets.lock` before failing, and the error now names the file, its actual length, and what deleting it costs: it is the key every stored secret is encrypted with. A key file that is young is still treated as a racing first run and waited for.

- Files PeaProxy owns are now replaced atomically, through one `fslock.WriteAtomic`: config, harness configs written by `clients connect`, compat data, `usage.json` and the request log. Previously each wrote to a fixed `<path>.tmp` (or, for `usage.json`, truncated the live file in place with `os.WriteFile`), so a crash mid-write left a truncated file and two PeaProxy processes writing the same harness config shared one scratch file. The temp file is unique per write, sits beside the target so the rename stays on one filesystem, is flushed before the rename, and is removed if anything fails. On Windows the swap goes through `fslock.Rename`, which already retries while a harness holds the file open.

## v2.0.10

- The Pi preset is a `~/.pi/agent/models.json` that overrides the built-in `anthropic` (no `/v1`) and `openai` (`/v1`, Responses) providers, so pi keeps its bundled model metadata. The old preset exported `ANTHROPIC_BASE_URL` / `OPENAI_BASE_URL`, which pi never reads. `clients connect pi` now writes those two overrides (merging into existing entries) instead of printing the snippet, and `disconnect pi` removes only fields it owns. Live-verified with pi 0.87.1 on both wires, including tool calls. See [HARNESS.md](HARNESS.md).
- `clients connect` for JSON configs could drop the closing brace when the same file was edited more than once (a slice-capacity aliasing bug in the key-preserving writer); fixed.
- The OpenCode preset declares per-model `limit`, `modalities` and `variants`, uses `@ai-sdk/openai` for GPT, and keeps `peaproxy-*` provider ids. See [HARNESS.md](HARNESS.md).
- An OpenAI-wire client on a Claude account no longer receives `finish_reason` + `[DONE]` after the upstream stream failed mid-turn.
- `clients connect claude-code` writes `ANTHROPIC_BASE_URL` (no `/v1`), `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL` into the `env` block of `~/.claude/settings.json`, keeping other `env` keys; `disconnect` removes them only while `ANTHROPIC_API_KEY` is still `peaproxy`. `connect opencode` is now guided and prints the preset, because a working OpenCode provider needs per-model metadata. Before this, both wrote a top-level `"peaproxy"` key that neither harness reads; both disconnects still remove it.
- Antigravity honours a Cloud Code weekly-quota reset hint (up to 7 days) instead of clamping it to 1 hour and retrying a spent model every hour. A stream error that carries only a `google.rpc` status name now maps to its HTTP code, so it fails over like the same error on a non-streaming reply.
- `peaproxy completion <bash|zsh|fish|powershell>` writes a completion script to stdout. Command and flag names come from the command tree; client presets (`clients show|verify|connect|disconnect`), account presets (`accounts add`) and the model and provider ids already in `config.yaml` and `usage.json` (`catalog pin|rename|hide`, and `catalog hide --kind provider`) are completed too. That part reads only those two files, so a tab key makes no network call, opens no keychain prompt, and cannot fail on a config being edited — the live catalog is left to `peaproxy models list`. An unsupported shell is an error naming the supported ones, not help text with a zero exit.
- Client connect: Connect from the web UI and admin API writes the address the server is actually listening on (loopback for an unspecified bind, brackets for IPv6) instead of `127.0.0.1:8317`. `GET /admin/clients` and guided-connect snippets and verify hints follow the same port (the hint gains `--origin` off the default), and `peaproxy clients show --origin` (or guided `connect --origin`) prints them for another address. Every managed client now has a Connect button in the web UI, Pi included: each entry in `GET /admin/clients` carries `connectable`, and the UI renders its buttons from that instead of a list of names it kept for itself, which is how Pi went missing from it. `connect pi` honours `PI_CODING_AGENT_DIR` and writes `$PI_CODING_AGENT_DIR/models.json` when it is set, rather than always `<root>/.pi/agent/models.json`. Connect rejects a base URL that is not http(s), has no host, or contains `"`, `\` or control bytes, and a model with those bytes or longer than 256 bytes (400). Strings written into Codex TOML and Continue YAML are fully escaped. Multi-line JSON configs keep their indent and trailing newline, and an existing `env` / `providers` key (or Pi provider entry) stays where it was instead of moving to the end, so connect then disconnect restores the file byte for byte. Disconnect does not rewrite a file that holds no PeaProxy keys. A Claude Code `env` or Pi `providers` value that is not an object is refused (400) and the file is left alone; missing or `null` still counts as empty.
- `--origin` means the same thing on every `clients` subcommand: the bare gateway origin, with one trailing `/v1` accepted and normalized away. `connect` then gives each client the suffix its wire needs, so pasting the origin a user copied out of `clients show`, `clients verify` or the UI's verify hint into `connect` produces a working config. Previously the bare origin was written into codex, continue and pi verbatim, with no `/v1`, and those clients could not reach the gateway. The origin logic lived in three places (`server.defaultOrigin`/`withOrigin`/`verifyHint`, `clients.WithOrigin`, and a fourth copy of the default in `verify.go`); it is now `clients.NormalizeOrigin`, `clients.VerifyHint` and `clients.WithOrigin`.
- Connect and disconnect no longer reformat the parts of a client config they have no business touching. A compact array (`"allow": ["Bash(ls:*)"]`), a nested object written inline (`{ "FOO": "bar" }`), the spacing inside a single-line object, and a file with no trailing newline all survive a connect/disconnect round trip byte for byte; only the value PeaProxy writes is laid out, and only in the style of the object holding it. A new or empty object it creates is still spread over the file's lines rather than appended on one. The Codex block is inserted after a blank line and takes the blank line back out again on disconnect, and the file's trailing newline and CRLF endings are preserved in both directions. Previously the whole document was re-indented with `json.Indent`, which expanded compact arrays; re-indenting is also what made nested edits look right, since marshalling a `json.RawMessage` compacts it.
- Codex OAuth: chat completions carry `service_tier` (`fast` → `priority`; `priority` and `flex` pass through), `reasoning_effort` (as `reasoning.effort`) and `parallel_tool_calls` (only when sent) into the Responses body. Every `/responses` call sends `x-codex-routing-hint: model=<m>[;tier=<t>]` built from the posted body; it is skipped when a value is empty or unsafe.
- Claude OAuth: SSE lines rewritten to restore an aliased tool name keep their CRLF and spacing.
- Streams: a native Responses stream ending in `response.incomplete` commits like `response.completed`. `response.failed` before the first committed event is a prelude error, so the request fails over instead of waiting out `preludeTimeout`. A translated Responses stream whose upstream breaks off after `response.created` now ends with `response.failed` (previously the stream just ended). An OpenAI-wire `error` chunk from an OpenAI-compatible upstream now ends a translated `/v1/messages` stream with an `error` event and a translated Responses stream with `response.failed`, instead of a completed turn.
- Responses wire: a translated turn that stopped on the token limit or a content filter reports `status: incomplete` with `incomplete_details.reason` `max_output_tokens` or `content_filter`, and the stream ends with `response.incomplete`. Other finishes are unchanged.
- Antigravity: a blocked prompt (`promptFeedback.blockReason`, no candidates) finishes as `content_filter`. A type list next to `anyOf`/`oneOf` keeps only the branches the list allows (integer fits `number`), falling back to the union when none fit. An array parent without `items` takes the `items` of every `anyOf` branch that has them.
- Secret store: every operation on either backend holds `secrets.lock` next to the config (15 s wait), so a server and `peaproxy auth login` saving together no longer drop each other's entries. `secrets.enc` is written through a unique temp file and renamed, `secret.key` is created exclusively so racing first runs agree on one key, and the keychain probe item name is unique per process.
- Config: writers hold `config.lock` (15 s wait) and replace `config.yaml` atomically. Server saves merge with the file on disk instead of overwriting it: accounts added or re-logged-in by another process are kept, accounts the server removed are removed, and settings the server did not change are taken from disk. On that save the server adopts providers, `hide`, `expose`, `catalog` and `routes` from the merge without a restart. `peaproxy auth login` updates the file under the lock and no longer writes `PEAPROXY_*` overlays (such as `PEAPROXY_PORT`) into it. A refreshed OAuth token whose save fails stays in memory and the request succeeds; the failure is logged once per distinct error. An account whose stored secret cannot be read during that merge keeps its in-memory token instead of adopting the token-less copy.
- Read-only config dir: a config directory without write access works again for reading. `EnsureFile` loads an existing `config.yaml` without taking `config.lock` (it locks only to create the file), and secret reads fall back to unlocked reads when `secrets.lock` cannot be created because of a permission error or a read-only filesystem. Every write still requires the lock.
- OAuth refresh is atomic per account. One refresh runs at a time per account, it runs on a context detached from the caller's cancel and deadline (so a request that ends after the provider answered cannot lose a rotated refresh token), the token is re-read inside that flight (so a caller holding a stale snapshot does not present an already-rotated token), and the new token is committed inside it (so a caller arriving afterwards cannot start a second refresh). A login and a refresh now serialize on the same lock, and the generation check, the in-memory store and the save happen under it, so a login landing mid-refresh is what ends up on disk. All six OAuth adapters (`anthropic_oauth`, `openai_oauth`, `kimi_oauth`, `xai_oauth`, `antigravity`, `copilot_oauth`) go through one `oauth.Ensure` instead of six hand-rolled copies of the same sequence.
- Copilot: the GitHub access token is treated as a secret, so it no longer lands in `config.yaml` in the clear (it lives in the keychain or `secrets.enc` like the other tokens) and is redacted from request-log previews. A rotated refresh token in the token-endpoint response is now read and kept; previously it was discarded and the spent token was persisted, and the response was not even parsed for it. The adapter's `apiBase` write is taken under the request-path lock, which it previously was not.
- Errors: `/v1/chat/completions` and `/v1/responses` now answer `{"error":{"message","type","param","code"}}` and `/v1/messages` answers `{"type":"error","error":{"type","message"}}`, with `type` derived from the status (400 `invalid_request_error`, 401 `authentication_error`, 403 `permission_error`, 404 `not_found_error`, 413 `request_too_large`, 429 `rate_limit_error`, 502/500 `server_error` / `api_error`, 503 `server_error` / `overloaded_error`). OpenAI and Anthropic SDKs read those two fields, so a rate limit is no longer reported to them as an unclassified string. `/admin/*` and the pre-routing middleware keep the plain `{"error":"…"}` string form.
- Errors no longer carry the upstream response body. A provider can echo a prompt fragment or a credential back inside its error JSON, and that text was reaching the client verbatim; the message a client sees is now the status plus, where it helps, the reason (`all matching accounts in cooldown: upstream HTTP 429`). `Retry-After` is unchanged, and the full text stays in the local request log.

## v2.0.9

- The client's `anthropic-beta` header is forwarded to Anthropic, merged after PeaProxy's own betas (both `anthropic` and `anthropic_oauth`). OpenCode's adaptive thinking sends `thinking.block_binding` (captured on Claude Opus 5.5), which Anthropic rejects without the `thinking-binding-controls-2026-08-01` beta the client asked for. Opus 5.5, Sonnet 5 and Fable 5.1 tool calls from OpenCode were live-verified on an Enterprise OAuth account. Names are checked at the HTTP boundary (letters, digits, `-_.`; at most 16, 64 characters each); anything else is dropped. `anthropic_oauth` never forwards `context-1m-*` (the subscription lane rejects it without extra usage, as before), and `anthropic` never forwards `oauth-*` (it conflicts with `x-api-key`).

## v2.0.8

- Claude subscription OAuth on a Team/Enterprise workspace no longer rejects OpenCode as a third-party app (as of 2026-09; the classification is Anthropic's and can change) ("Third-party apps now draw from extra usage"). OpenCode's core tools are sent under Claude Code's names (`bash` → `Bash`, `read` → `Read`, …) and renamed back in responses. See [OAUTH.md](OAUTH.md).

## v2.0.7

- `preludeTimeout` defaults to 30s (was 5s). A slow first event moves to the next account only when another can take the request, never retries the same account, and never starts a cooldown. The last reachable account is bounded by `deadline` alone.
- Cooldowns last 30s or the upstream's reset hint (`Retry-After`, or the Antigravity / Cloud Code error body), clamped to 1s–1h. A transport failure (502, 504, edge connect error 503) is retried once and cools for only 5s. The 503 names each cooled account and its cause. The `Retry-After` sent to clients is capped at 60s.
- OAuth tokens above the macOS keychain item limit are stored as chunked keychain items, header written last. An unreadable stored secret is treated as absent with a stderr warning; only that account logs in again. One account's failed secret write no longer stops the others from being saved. Chunks left by an interrupted save are swept by a later write.
- Translated `/v1/messages` streams emit tool calls as `tool_use` blocks, carry usage, report `max_tokens` on truncation and `refusal` on a content filter, and end with an `error` event (never a completed tool turn) when the upstream breaks off mid-stream. While tool arguments buffer, a `ping` is sent when a tool-call delta arrives and at least a second has passed since the last event.
- Antigravity: tool calling both directions, tool schemas reduced to the Gemini Schema proto (tuple `items` included), `gemini-3.1-pro-high` / `gemini-3-pro-high` sent as `gemini-pro-agent`, 429 / 503 capacity errors cool only that model, and safety stops finish as `content_filter`.
- Finishing an OAuth login from the web UI refreshes the catalog. An older catalog refresh that finishes last no longer replaces a newer one.
- The account a request is attributed to is the last one actually called. Cooldown errors also name accounts that are between cooldown and their recovery probe.

Known limits:

- A keychain reader racing another process's token rewrite retries up to 3 times. Since v2.0.10 this only matters for a PeaProxy binary older than v2.0.10 sharing the config directory.
- Chunks left by an interrupted save are reclaimed by the next write instead of after 30 minutes. Every writer takes `secrets.lock` and so does every sweeper, so an entry a sweeper can see is an orphan by definition — a writer still alive would be holding the lock the sweeper just acquired. Age said nothing; the wait did. (The one entry that *is* still protected is the generation a header currently points at, which the sweeper re-reads before deleting anything.)
- `peaproxy auth login`, `catalog …` and other CLI writers wait up to 15 s if the running server is mid-save (or blocked on a keychain prompt), then fail with `config <dir> busy (another peaproxy process is saving)` or `secretstore: <dir> busy (another peaproxy process is saving)`; retry the command.
- If the server cannot write its config (unreadable YAML on disk, secret store busy), a refreshed OAuth token is kept in memory and the request still succeeds; the write is retried on the server's next save and the failure is logged once per distinct error. Restarting the server before a successful save loses the refreshed token and that account refreshes again on first use.
- A config file the server cannot read blocks all of its saves, including token refreshes and UI changes, until the file is repaired.
- When the server and another process both changed the same account, or the same top-level setting, the server's copy wins.
- An OpenAI-wire `error` chunk that arrives before any output on a translated `/v1/messages` or `/v1/responses` stream is returned to the client as an error; it does not yet fail over to the next account.
- Changes another process writes to the config are picked up by a running server on its next save, not the moment the file changes.
- Chat completions on a Codex OAuth account still do not forward `verbosity` or `prompt_cache_key`, and drop any `service_tier` other than `fast`, `priority` or `flex` (Codex omits the field for the default tier).
- `gemini-3.1-pro-high` → `gemini-pro-agent` was not live-verified on the release binary (weekly quota exhausted); `gemini-3-pro-high` and the flash models were.
- The user-reported 429 was not reproduced directly. The cooldown cascade and the Cloud Code throttle blackouts were.
