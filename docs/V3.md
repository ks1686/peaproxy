# PeaProxy v3

v3 makes PeaProxy opinionated. You point your existing client at it as one more
provider, and it aggregates accounts, exploits free tiers, carries context across
providers, and routes for cost — without you changing your client config or
turning anything on.

The promise it is built around:

> Spend less to fulfill the same request — not fulfill a cheaper version of the
> request.

Every design decision below follows from the second half of that sentence. A
saving that changes the answer is not a saving, and a proxy that silently
downgrades your work is worse than one that costs more.

## What v3 will not do

These are guarantees, not aspirations, and each is covered by a test.

- It will not substitute a different model for one you named explicitly. Exact
  means exact.
- It will not reduce reasoning or output limits on your behalf.
- It will not summarize or truncate tool output.
- It will not replay a cached agent response as if it were a fresh one.
- It will not edit your instructions.
- It will not invent a `finish_reason` or terminal event to make a truncated
  response look complete. A stream that dies mid-body is announced with an
  error carrying `stream_incomplete`; see [D1](#the-stream-ended-without-finish_reason-incident).
- It will not report an unknown price as zero, free, or unlimited. Unknown stays
  unknown, because an overstated bill is as unacceptable as an understated one.

## Upgrade

Your client config does not change. If it talks to PeaProxy today, it keeps
working.

The config gains an optional `optimization` block. **Existing configs need no
edit.** A config without the block gets the v3 defaults; a field you set
explicitly always wins.

```yaml
optimization:
  policyVersion: 1
```

`policyVersion` is checked. A file written by a newer PeaProxy is refused with a
clear message rather than silently misread by an older binary.

### Defaults, and how to turn them off

Everything below is the default. Each is listed with the setting that restores
the pre-v3 behaviour.

| Default | Setting to change it | Notes |
| --- | --- | --- |
| Optimizations applied automatically | `optimization.automatic: false` | Turns off the whole safe set at once |
| Prompt cache optimized where supported | `optimization.promptCache: preserve` or `off` | An existing `requestEngine.promptCache` still wins |
| Context optimization on | `optimization.contextOptimization: false` | Also follows `automatic` |
| Exact models stay exact | — | Not configurable. This is a guarantee, not a default |
| `pea/free` never spends | — | Not configurable |
| `pea/local` stays on this machine | — | Not configurable |
| Local assistant off | `optimization.localAssistant: true` | Also needs an endpoint; both are required |
| Context artifacts in memory only | `optimization.persistentContext: true` | Off by default |
| Anonymous providers refused | `optimization.allowAnonymousProviders: true` | Off by default |
| No spend ceiling | `optimization.spendCeilingUSD: 25.0` | Zero means *unset*, never "unlimited is fine" |

The three non-configurable rows are deliberate. They are the promises above, and
a setting that could switch them off would not be a promise.

### Money guards

Two settings exist because spending someone else's credentials by accident is
the worst failure this tool could have.

- `optimization.freeOnly` refuses any deployment that cannot prove the call will
  not be billed. It refuses with an explanation naming the setting rather than
  failing quietly.
- `optimization.spendCeilingUSD` caps spend in a rolling window. **It fails
  closed.** If recorded spend cannot be measured, PeaProxy refuses rather than
  proceeding, because the accounts whose prices are least known are exactly the
  ones where guessing wrong spends money.

## What "free" means here

v3 classifies allowance honestly, because the alternative is a routing decision
made on a claim nobody checked.

Recognized: recurring free tier, finite trial, one-time promotional credit,
subscription-included, local, and paid. A one-time credit is not a recurring
free tier, and a subscription's marginal API spend is not a claim of zero total
ownership cost.

Where a free claim cannot be measured, PeaProxy records it as unknown rather
than assuming the friendly reading.

## Providers you add

Presets are grouped in the UI so the free tiers are findable. Presets marked
**not verified** have never been tested against a live account; PeaProxy shows
that rather than implying an integration that was never exercised. The marker
stays permanently unless a real account confirms it.

Cache read/write pricing is currently known only from OpenRouter. Elsewhere,
cache warmth is used only as a tie-breaker between otherwise equal candidates —
never as a reason to prefer one deployment over a cheaper one, and never when
either price is unknown.

## Portable context is not a portable cache

Context PeaProxy carries between providers is its own notes, re-derived from
what you sent. It is never a replay of a previous provider's answer.

**Provider-side prompt caches do not migrate.** A cache warm on one provider is
cold on the next, and PeaProxy never pretends otherwise or counts that as a
saving.

Stored artifacts are scoped to your session and process. Persistence to disk is
opt-in.

## Proxy-owned retrieval

When the client uses tools and the provider supports them, PeaProxy may add one
tool of its own, `pea_search`, to retrieve relevant earlier context. This costs
extra tokens, so it is capped and measured rather than assumed free.

Constraints, all enforced:

- **Streaming clients are not offered the tool.** Answering a tool call
  mid-stream would mean buffering the response, defeating the incremental
  delivery you asked for. Streaming requests use pre-retrieval instead.
- **Rounds are capped** (`MaxRounds = 4`).
- A search that finds nothing says so. It never invents a passage.
- The caller's own tools are never answered by PeaProxy. Those belong to your
  client.

## Local assistant

Off by default, and it does nothing until you both enable it and name an
endpoint. When enabled, the endpoint must be on the loopback interface — there
is no setting that allows anything else, because a helper described as local
that can be pointed at a remote host is not one.

## The `stream ended without finish_reason` incident

If you saw that error, it was PeaProxy's fault and it is fixed.

Some accounts (`gpt-6-astra` on the ChatGPT-hosted backend, and the
`google-oauth` account) speak the Responses API upstream and are **translated**
to Chat Completions for your client. On a clean upstream end, the translator
always wrote a terminal event. On a **mid-stream transport error** it returned
first — leaving you holding a partial response that simply stopped, with no
`finish_reason`, no `[DONE]`, and no error to act on.

The fix writes a terminal error carrying `stream_incomplete` and deliberately
does **not** write a `finish_reason`. A cut stream is announced, never completed.

If you still see this error, please report it with the account and model. The
same class of bug may remain on a wire not covered by the fixture tests, which
are not a substitute for testing against a live account.

## Rollback

- **Disable v3 behaviour:** set `optimization.automatic: false`. This restores
  pre-v3 optimization behaviour and is reversible at any time.
- **Full revert:** downgrade the binary. No data migration is involved; the
  `optimization` block is ignored by older builds.
- **Stored context:** clearing artifacts costs nothing but the carried context
  for that session.

## Known limitations

Stated plainly, because a proxy that overstates itself is the problem this
project exists to fix.

- **No provider has been verified against a live paid account.** Conformance is
  tested with fixtures; fixtures are not providers.
- **Eight presets are documented-only** and display `(not verified)`.
- **Cache read/write rates are known only from OpenRouter.**
- **Retrieval savings are not yet quantified.** The routing savings are
  demonstrated by the promotion gates in `internal/eval`; retrieval savings are
  not, because measuring them needs real provider pricing.
- **Free-tier classification is best-effort** from official documentation, and
  providers change their terms without notice.
- **OpenAI-compatibility is a family resemblance, not a guarantee.** DeepSeek
  `reasoning_content`, Z.AI `thinking`, and Alibaba `enable_thinking` are real
  per-provider divergences.

## How the promises are checked

`internal/eval` states each claim as a scenario that can fail, and CI runs them
as a promotion gate. Scenarios use local stubs with known prices, so a scenario's
cost is arithmetic rather than an estimate.

Cost is asserted as well as behaviour, because a cheaper answer is only a saving
if it is the same answer.

This is not decoration. The first time the suite ran, it found that the spend
ceiling was written, tested, and never called — the money guard did nothing at
all.
