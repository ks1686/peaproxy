## T12 — deterministic conformance and quality/cost evaluation

Order: fixture harness can be parallel-safe after T3; final evaluation serial after T10/T11.
Files: internal/evals/replay_test.go, routing_test.go, context_test.go, testdata/manifest.json (new); cmd/peaproxy-eval/main.go (new); docs/research/v3-evaluation.md (new); .github/workflows/ci.yml.
Input: mock protocol fixtures plus consented, sanitized task corpus. Output: reproducible reports comparing pass-through baseline, cache-only, routing-only and combined optimization.

Red: evaluator rejects fabricated savings, missing attempt costs, duplicated usage, missing finish_reason, tool ID corruption, unauthorized provider choice, unknown cost treated as zero, or unmatched task outcomes. Include rare buried errors, exact identifiers, repeated-but-changing values, long context, multi-tool turns, structured outputs, multilingual text and provider switches. Do not test only highly compressible successful examples.
Green: deterministic validators for code/tests/extraction and blinded human review where automatic grading is insufficient. Report task success, final correctness, tool/schema fidelity, dollars where known, estimated cost separately, cache hits/writes, total turns, p50/p95 latency, failures and local overhead. Store per-case routing and bypass reasons.

Default promotion gates:
- Zero protocol/capability/privacy/free-only/local-only violations across the fixture corpus.
- Zero regressions on exact-value and tool-fidelity assertions.
- At least 100 paired representative task evaluations for each default-changing routing/compression policy; report confidence intervals and failures, not a universal no-quality-loss claim. If evidence is inconclusive, keep the policy disabled for that task/profile.
- No observed task-success regression in the promotion corpus; maintain noncompressible controls. Investigate every regression rather than averaging it away with easier tasks.
- Net measured savings after extra turns on eligible workloads; where price is unknown, report token effects only. Cache-cold and cache-warm sessions both included.
- Target deterministic policy overhead below 10 ms p95 on a documented reference machine. Measure local/model/retrieval latency separately; do not hide it inside that target.

Proof: `go test ./internal/evals -count=1`; `go test ./internal/evals -bench . -benchmem`; `go run ./cmd/peaproxy-eval --fixtures internal/evals/testdata --mode offline --output /tmp/peaproxy-v3-eval.json`. Implement this exact CLI contract in this task. Live evaluation requires an explicit approved provider list and budget, refuses execution without both, and never silently uses another model when selected hardware/provider is unavailable.

### T12 — promotion gates

`internal/eval` states the product's claims as scenarios that can fail, and CI
runs them as a promotion gate. Eight promises, each with the consequence of
breaking it recorded next to it, because a gate nobody can explain is a gate
nobody will fix.

The harness uses local stubs with known prices, so a scenario's cost is
arithmetic rather than an estimate. A gate that depends on live provider
pricing fails for reasons unrelated to the code under test.

Every scenario checks cost *and* equivalence. That is the point: a cheaper
answer is only a saving if it is the same answer, and the second claim is the
one that usually gets skipped.

What running them found, on the first attempt:

- **The spend ceiling was never called.** `ceilingBlocks` was written, tested,
  and unreachable -- the fifth unwired helper in this branch, and the most
  dangerous, since it is the money guard.
- **The ceiling had no data even once wired.** `spendWindow` was never bound to
  the usage ledger, so it read a permanent zero and could never fire. Fixed
  with `SetUsage`, which rebinds both together; assigning the store alone leaves
  a guard that is quietly inert.

Both were found by an eval, not by a unit test, which is the argument for
having one.
