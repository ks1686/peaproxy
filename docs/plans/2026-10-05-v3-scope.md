Breaking config changes are acceptable in v3: the maintainer authorised them and users can migrate. Two limits on that authorisation. Schema and preset shape may change freely with a documented migration. A routing-behaviour change for users who never opted in -- tightening what counts as a free route, for example -- is not a migration a user can perform, so it lands as a documented breaking change that fails loudly with an explanation rather than as a quiet behaviour shift.

Addressing all issues means an explicit disposition, not silently implementing risky suggestions. Proposed release notes must distinguish shipped work from deferred adapters. Do not close deferred issues as implemented.

## Defects and evidence

### D1 — repeated live stream failure; release blocker

User repeatedly reported `stream ended without finish_reason`, then a retry failure while the plan was being written. No exact retry error text supplied. See [incident record](2026-10-05-v3-stream-incident.md). Actual wire, upstream and root cause remain unverified. T1 owns reproduction, repair and affected-client validation. Keep retry failure as a related symptom until traced, not a confirmed second cause.

### D2 — native stream usage undercount; reproduced at parser level

`internal/usage/parse.go` only decodes top-level usage and replaces rather than merges stream samples. Isolated tests at baseline produced:
- Anthropic message_start input=12 followed by message_delta output=7 → input=0/output=7.
- Responses response.completed containing response.usage input=12/output=7 → usage unknown.

T2 adds permanent wire fixtures and verifies server integration. This does not establish the cause of D1.

### D3 — cache counters ignored; reproduced

ApplyPublishedUsage with prompt_tokens=100 and prompt_tokens_details.cached_tokens=80 leaves Event.CacheRead=0. CacheRead/CacheWrite exist in usage structs but the published-usage parser does not populate them. T2 owns provider-specific parsing and accounting.

### D4 — automatic routing misses simultaneous model cooldowns; reproduced

`internal/gateway/engine_route.go` snapshots slots.anyActive, which chooses only one active slot. With model `other` cooling for one minute and `m` for one hour on acct-a, pickAutomatic still includes acct-a/m. T1 must test every candidate against its own cooldown; verify actual attempt behavior separately.

### D5 — free eligibility uses another account's price; reproduced

priceFor looks up model ID without deployment/account identity. Catalog rows acct-a/m priced zero and acct-b/m priced 4 cause automaticKind(pea/free, acct-b/m) to return true. Reproduced eligibility error, not a claim that an actual bill occurred. T3 scopes quotes and T6 tests end-to-end routing and fallback.

### D6 — cache optimization rewrites unrelated request bytes; fixed

**Was:** `internal/promptcache/policy.go` insertBreakpoint unmarshalled the
whole request into `map[string]json.RawMessage` and marshalled it back. Go
sorts map keys, so every key in the body moved to alphabetical order, the
caller's whitespace was dropped, and each block's fields were reordered. A
prompt cache only hits when the bytes before the marker are identical, so this
guaranteed a miss on every turn -- silently, with requests still succeeding.

Observed directly: a body beginning `{"zebra": ..., "system": ..., "alpha": ...}`
came back as `{"alpha": ..., "system": ..., "zebra": ...}`.

**Now:** the marker is inserted into the original bytes. `json.Decoder` is used
only to locate the `system` value and its last element; every other byte of the
request is copied verbatim, including key order, spacing, escapes and number
formats.

**Evidence:** eight fixtures pin byte preservation, key order, valid JSON, the
empty-block case, the untouched cases, last-block placement and idempotence.
Mutation-checked: restoring the map-remarshal implementation fails
`TestInsertBreakpointPreservesEveryOtherByte` and
`TestInsertBreakpointDoesNotReorderKeys`.

Not measured here: the token-level saving on a real provider. That needs a live
key and is listed in the provider evidence gaps.

### D7 — session affinity on automatic routes; disproved

**Not a defect.** The suspicion was that success bookkeeping binds affinity under the resolved model while pickAutomatic reads it under the route alias, so an automatic route could never match. That reading was incomplete: prepare returns the caller's alias separately, and every success path binds both keys (`g.rememberSuccess(session, model, …)` and `g.rememberSuccess(session, client, …)`). The alias key pickAutomatic reads is therefore always written.

Four tests now pin the behaviour, including a mutation check that disables the pin and confirms the tests fail: honouring an existing bind, writing both keys on success, leaving the exact-model key untouched, and ignoring an expired bind. Losing this would move a conversation between accounts and discard the provider's warm prompt cache.

Refs T6.

## Provider verification tiers

The maintainer has no paid provider subscriptions, so a live call to a metered
provider is not available. Verification is therefore tiered, and a preset may
sit in a lower tier indefinitely rather than being promoted on a guess.

**Live-verified.** A real key exists and PeaProxy has completed a call. The
maintainer has offered to sign up where a usable free tier exists. Only these
presets may back a claim that a provider works.

**Conformance-verified.** PeaProxy's own adapter is exercised against the
provider's *documented* wire format, captured as fixtures: response envelope,
usage block, streaming frames, error shape, and provider-specific fields such
as DeepSeek `reasoning_content`, GLM and Z.AI `thinking`, Alibaba
`enable_thinking`. No credential is needed and nothing is claimed about live
behaviour. This is the tier most new presets should reach, and it is testable
without spending money.

**Documented-only.** Base URL and limits come from the provider's documentation
and are marked `Unverified`. Nothing is claimed beyond the documentation.

One thing this policy rejects: passing an off-the-shelf adapter for a
similar-shaped provider. OpenAI-compatibility is a family resemblance, not a
guarantee. A working Groq key says nothing about whether PeaProxy parses
DeepSeek's reasoning field, so conformance fixtures are required per provider
rather than inherited.

### Sign-up shortlist

Confirmed free to try, and worth a real key:

- **Cohere** -- trial keys at 1,000 calls/month. This is the only one of the
  eight new presets known to carry a free trial, so it is the best single
  choice for moving a preset from documented-only to live-verified.

Still unconfirmed and to be checked before any tier is claimed: whether
DeepSeek, Mistral, Z.AI, minimax, Together, Fireworks and Alibaba offer any
trial credit or free tier. These pages are JavaScript-rendered, so the earlier
research pass did not capture them and the presets stay `Unverified` until
someone reads the pricing page. No free tier may be inferred for a provider
whose documentation was not actually read.

### Presentational decisions, closed

**The unverified marker stays.** Presets whose endpoints PeaProxy has never
called render as "Label (not verified)" in the dropdown, and selecting one
shows a note saying so. It looks unfinished, which is the correct impression: a
bare label would imply a tested integration. The marker is the honest state,
not a temporary badge awaiting cleanup.

**The admin presets payload change is additive and needs no migration note.**
`group` and `unverified` are new fields on an existing response; no field was
removed or retyped. The one removal is the two dead OAuth *presets*, which
belonged to `GET /admin/presets` only. The `qwen_oauth` and `factory_oauth`
adapters remain registered, so this does not affect anyone who configured one.

## D8 — `freemium` is doing too much work

Discovered while writing the provider evidence record. Cerebras and Hugging
Face are tagged `freemium`, and the v2 research pass found that Cerebras's
$5 balance is a **one-time promotional credit** and Hugging Face's free
allowance is **$0.10/month**. Neither is a recurring allowance.

Why it matters, checked rather than assumed: `automaticKind` does **not** read
the tier tag. `TierFreemium` is consulted nowhere in routing; only
`TierLocal` is. So the original framing of this defect -- "the tier tag makes a
metered provider look free" -- was wrong, and the tier tags are not the bug.

The real exposure is narrower and was confirmed in the code:

- `RouteFree` treats a verified `0/0` price as proof of free.
- The only producer of a verified price in the tree is `openRouterPrice`, so
  catalog-sourced free routes come from OpenRouter rows.
- A user-supplied `automaticRoutes.prices` override can inject `0/0` for **any**
  deployment, including a metered one. That route is then treated as free and
  will bill the moment real capacity runs out.

So this is a money bug in the **price-based free proof**, reachable through a
config override, not in the tier tags. The tags still need correcting for
accuracy of what the UI shows a user; the routing fix is separate.

Disposition, after attempting the routing fix and finding it wrong: **do not
change `RouteFree` behaviour.**

A first attempt made a `0/0` price count only when the catalog independently
reported the same zero. It broke `TestFreeRouteUsesVerifiedZeroOnly`, and the
test was right to break. A user who configures a 0/0 price is stating a fact
they know about their own account; the catalog has no opinion about promotional
credit, and refusing the value because nothing corroborates it makes the
documented escape hatch useless. The rule is the other way round:
**contradiction blocks, absence of corroboration does not.**

What the attempt did surface is the real gap. A price a user configured and a
price a provider published were both `catalog.Price{Verified: true}` with no way
to tell them apart, so economics would apply one rule to a measured fact and an
asserted one. That is now closed: configured quotes carry
`Source: PriceSourceConfig`, published quotes keep their publisher, and
`economics` applies the strict rule to the asserted case.

Two things still need doing, neither of which changes routing behaviour:

1. Allowance observations gain a kind: `recurring`, `promotional`, or
   `one_time_credit`. The first two expire differently and the third has
   already been spent by definition.
2. `economics` refuses an asserted price where a published one would do, so a
   free-only guarantee rests on measurement rather than on the user's memory.

Both are now shipped, with one deliberate narrowing. `GuaranteesFreeTo` and
`FreeForTrustedUse` exist and are tested, but the routing filter
(`freeOnlyAllows`) does not call them: under `freeOnly` a user-configured zero
is honoured, because the user turned the safety on and stated the fact in the
same breath, and a promo credit appears nowhere in ListModels. The strict
`Measured()` rule is kept for surfaces that make a promise *about safety* to
the user rather than for filters that route requests.

`optimization.freeOnly` had been dead config since T3. It is now enforced on
every automatic route, not only `pea/free`, and a refusal names itself:
"no deployment has a verified zero price" instead of the generic "no eligible
model". `TestFreeOnlyFailsTheRequestRatherThanFallingBackToPaid` asserts the
request fails and neither upstream is contacted, because a candidate filter
that let a later fallback through would still spend the money.

Owner: shipped. Until then a configured 0/0 is honoured, which is the correct
default: an over-cautious router costs money, an over-confident one spends it.

Retagging is separate and still not done:

- A tier tag is never by itself proof that a call is free. `GuaranteesFree`
  must require an allowance observation that is both current and of a
  recognised kind.
- Allowance observations gain a kind: `recurring`, `promotional`, or
  `one_time_credit`. The first two expire differently and the third has already
  been spent by definition.
- A promotional or one-time balance reports as unknown once it is gone, not as
  zero and not as free.

Owner: T6. Until then these two routes stay tagged as they were, which is the
conservative direction: an over-cautious router costs money, a over-confident
one spends it.
